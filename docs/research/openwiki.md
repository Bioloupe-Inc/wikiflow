# OpenWiki as a reference for building and maintaining the wiki

Read on 2026-09-12 from the [langchain-ai/openwiki](https://github.com/langchain-ai/openwiki) source and its self-generated wiki, cloned locally at `../openwiki` (a sibling of this repository, not tracked here). OpenWiki is a CLI whose agent writes and maintains a source-grounded Markdown wiki for a codebase. Nothing was run; findings come from reading prompts, the durable-run code, and the pages the tool wrote about itself.

## How it compares with our direction

OpenWiki documents the system **as built**: every page is derived from source files, tests, and git history, and is regenerated by an agent on a schedule. Our wiki is the **accepted contract** for the merged version, authored by the developer and agent inside the same PR as the implementation ([ADR-0004](../adr/0004-separate-issues-system-contracts-and-proposals.md)). That difference means most of OpenWiki's machinery for autonomous multi-page runs (a durable page queue, per-page rollback, resumable checkpoints) solves a problem we do not have, since wiki edits ride ordinary PRs.

Its sophistication is on the grounding and durability axis, not on emergent structure. The information architecture is planned up front by a model in one bounded planning step ([repository-prompts.ts](https://github.com/langchain-ai/openwiki/blob/main/src/agent/repository-prompts.ts)). What does emerge from simple rules is everything derived from page bodies: directory indexes, the link graph, backlinks, provenance stamps, and source lists are all computed from the Markdown rather than authored. That split is the most transferable idea.

## Ideas worth taking

| Idea | What OpenWiki does | Fit for us |
| --- | --- | --- |
| Code owns what code can derive | The agent writes only page bodies and four frontmatter fields. Deterministic passes then validate Mermaid, rebuild every `index.md`, stamp broken links, project sources, and reconcile provenance. Indexes are never authored ([wiki-finalizer.ts](https://github.com/langchain-ai/openwiki/blob/main/src/agent/wiki-finalizer.ts), [index-sync.ts](https://github.com/langchain-ai/openwiki/blob/main/src/okf/index-sync.ts)). | Strong. A CI pass over `wikispec/` can own indexes, backlinks, link checks, and diagram validation, so page authors follow few rules and structure appears from links. |
| Evidence with content hashes | Each material claim cites `repo://path#L10-L20` resources versioned by a content hash. A mismatch means the cited code changed (stale); a missing file means unresolved. Line ranges carry relocation anchors so unchanged text that moved keeps its version ([resolver.ts](https://github.com/langchain-ai/openwiki/blob/main/src/claims/evidence/repository/resolver.ts)). | Promising as a review lens. If contract pages cite the code or tests that verify them, a PR check can list pages whose cited evidence changed but whose prose did not. That is exactly what a reviewer of a proposal needs to see in the viewer. |
| Stale means recheck, not retract | A stale marker obliges the next editor to confirm, revise, or retract that claim explicitly; the tool refuses a submission that ignores it ([guidance.ts](https://github.com/langchain-ai/openwiki/blob/main/src/claims/guidance.ts)). | Fits a contract wiki well: code drifting from a page may be a bug in the code, so the human decides. |
| Materiality test | "If the proposition were false, would it change a reader's architectural model, implementation decision, operational expectation, or safe change plan? If not, omit it." Atomic means one falsifiable idea, not one file or symbol ([guidance.ts](https://github.com/langchain-ai/openwiki/blob/main/src/claims/guidance.ts)). | Directly usable as the rule for what belongs on a page, in line with [ADR-0006](../adr/0006-write-concise-linked-wiki-pages.md). |
| Organize by system, not by source tree | The planner is told to organize around owned systems, runtime domains, and cross-system workflows, to use folders only when coverage warrants them, and never to emit a flat dump of unrelated pages ([repository-prompts.ts](https://github.com/langchain-ai/openwiki/blob/main/src/agent/repository-prompts.ts)). | Matches our `sandbox-file-sync` style of topic. The pre-planned hierarchy is the part we would leave out. |
| A routing page, not a table of contents | `quickstart.md` is written last, with the full page map, as a task-routing map for an agent: "for this kind of task, read these pages" ([quickstart.md](https://github.com/langchain-ai/openwiki/blob/main/openwiki/quickstart.md)). | Cheap and useful entry point for both agents and the viewer. |
| Per-page baseline commit | The page manifest records the git head and source fingerprint each page was last completed against. Updates consider only changes after that baseline ([page-manifest.ts](https://github.com/langchain-ai/openwiki/blob/main/src/generation/page-manifest.ts)). | Lightweight way to know how current a contract page is without claim sidecars. |
| Provenance advances only on body change | Before and after a run the body is hashed; `generated: {by, at}` moves only if the hash differs, so reformatting and no-op runs never churn metadata ([generated-provenance.ts](https://github.com/langchain-ai/openwiki/blob/main/src/okf/generated-provenance.ts)). | Good rule for any automated stamp we add. |
| Non-blocking repair markers | A broken internal link gets an HTML comment stamped above it; an invalid Mermaid fence is degraded to a text fence with the parser error in a comment. Neither fails the run; the next edit finds and repairs them ([wiki-link-validator.ts](https://github.com/langchain-ai/openwiki/blob/main/src/agent/wiki-link-validator.ts), [mermaid/wiki.ts](https://github.com/langchain-ai/openwiki/blob/main/src/mermaid/wiki.ts)). | Suits a wiki that changes inside PRs: warn inline, let review decide. |
| A user-authored brief the agent never rewrites | `openwiki/INSTRUCTIONS.md` holds scope and priorities. Agents read it as control metadata and do not edit it ([code.ts](https://github.com/langchain-ai/openwiki/blob/main/src/agent/prompts/code.ts)). | The replacement setup skill could seed the same kind of brief. |
| Managed pointer block in AGENTS.md | A `<!-- OPENWIKI:START -->…<!-- OPENWIKI:END -->` block points agents at the quickstart and states that source is authoritative and the wiki is just-in-time context ([AGENTS.md](https://github.com/langchain-ai/openwiki/blob/main/AGENTS.md)). | Same mechanism our setup skill already uses for its root instruction block. |
| Frontmatter that serves retrieval | Pages use Google's Open Knowledge Format: `type` required, then `title`, `description` written for search, `tags`, plus tool-owned `sources` and `verified` ([OKF spec](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)). | A small, portable frontmatter set worth adopting as is. |

## Relevant to the viewer

The visualizer builds the graph from links alone: each `.md` file is a node with `type`, `title`, `description`, and `tags` from frontmatter, size from body length, and edges from resolvable relative links, with reciprocal backlinks recorded. It serves locally or exports a static folder (`index.html`, `client.js`, `graph.json`) that GitHub Pages can host ([graph.ts](https://github.com/langchain-ai/openwiki/blob/main/src/visualize/graph.ts), [README](https://github.com/langchain-ai/openwiki#explore-your-wiki)). The graph builder is MIT-licensed and small; the client loads its libraries from a public CDN. It is a general explorer, not a review lens, so it does not answer the change-focused UX in [ADR-0006](../adr/0006-write-concise-linked-wiki-pages.md), but the static export path is a working precedent for a PR-reachable viewer.

## Maintenance loop

A scheduled GitHub Actions job runs the update daily and opens a PR rather than pushing, preserving partial progress on failure ([openwiki-update.yml](https://github.com/langchain-ai/openwiki/blob/main/.github/workflows/openwiki-update.yml)). A clean update is a no-op that touches nothing but a timestamp. The LEDGER evaluation replays git checkpoints and classifies every current wiki claim as supported, stale, invented, or unverified against the source at that commit ([evals/ledger/README.md](https://github.com/langchain-ai/openwiki/blob/main/evals/ledger/README.md)). Scheduled sweeps are not a current requirement for us; the classification vocabulary is still a useful way to talk about wiki health.

## Limits

These findings describe OpenWiki's design as read from its source and its own generated pages on 2026-09-12; they do not measure the quality of wikis it produces. OpenWiki's claims model assumes documentation follows code, so its staleness signal would need reinterpreting for a contract wiki where the page may be right and the code wrong. No decision here has been made; [ADR-0006](../adr/0006-write-concise-linked-wiki-pages.md) and the [open questions](../../.agents/handoffs/wiki-driven-dev-harness.md) remain the authority.
