# Spec Kit and OpenSpec as references for the wiki workflow

Read on 2026-09-12 from the [github/spec-kit](https://github.com/github/spec-kit) and [Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec) sources, cloned locally at `../spec-kit` and `../openspec` (siblings of this repository, not tracked here). Both are spec-driven development toolkits for coding agents. Nothing was run; findings come from their docs, templates, schemas, and skill prompts. The companion [OpenWiki note](./openwiki.md) covers the source-grounded wiki generator.

## How they compare with our direction

Both tools organize work as a per-change folder of planning artifacts that an agent drafts and a human reviews before code. Neither keeps a system contract the way our wiki does. Spec Kit writes one `spec.md`, `plan.md`, and `tasks.md` per feature and leaves what happens to them afterwards to the team ([spec-persistence.md](https://github.com/github/spec-kit/blob/main/docs/concepts/spec-persistence.md)). OpenSpec is closer: a `specs/` tree is the source of truth for current behavior, and each change carries a delta that merges into it on archive ([concepts.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)). Our wiki is OpenSpec's `specs/` tree with the archive step removed: the contract change and the code merge in the same PR ([ADR-0004](../adr/0004-separate-issues-system-contracts-and-proposals.md)).

Where they are heavier than we want: Spec Kit fixes a nine-command pipeline with templates that carry numbered requirement ids, priorities, and success metrics; OpenSpec fixes a requirement-and-scenario grammar with RFC 2119 keywords. Where they are simpler: OpenSpec's four principles (fluid not rigid, iterative not waterfall, easy not complex, brownfield-first) and its rule that a change is just files git already versions match our intent well.

## Ideas worth taking

| Idea | What the tool does | Fit for us |
| --- | --- | --- |
| Specs grow from changes, not from a bulk import | OpenSpec tells brownfield adopters not to document the whole codebase: the first change documents the slice it touches, and `specs/` fills in around real work. Existing PRDs are source material for exploration, not documents to convert, because a bulk conversion produces a large, stale spec nobody trusts ([existing-projects.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/existing-projects.md)). | Direct tension with [ADR-0003](../adr/0003-develop-an-independent-wiki-workflow.md), which has setup build the full initial wiki. Worth weighing: a seeded skeleton that pages grow into, versus a complete first pass that may be stale before anyone reads it. |
| Behavior, not code | A spec says what the system does in terms anyone could check. The quick test: if the implementation can change without changing externally visible behavior, it does not belong in the spec ([schema.yaml](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml), [writing-specs.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/writing-specs.md)). | Pairs with OpenWiki's materiality test as the second rule for what a wiki page carries. Our pages also hold design decisions, which OpenSpec keeps in a separate `design.md`. |
| Name the case you would be upset to see broken | Each requirement carries scenarios titled by the case they cover, and the authoring habit is to ask which failure would hurt most and make sure a scenario names it ([writing-specs.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/writing-specs.md)). | A light rule for acceptance evidence in the PR description without adopting the full GIVEN, WHEN, THEN grammar. |
| Describe a change as a delta | A change states ADDED, MODIFIED, REMOVED, and RENAMED requirements; MODIFIED carries the full new text, REMOVED carries a reason and a migration ([concepts.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md#delta-specs)). | Our PR already carries the diff of the wiki pages, so the delta is implicit. The vocabulary is still useful for the PR description and for the viewer's change lens: which pages were added, changed, or retired. |
| Read in the order that lets you quit earliest | Review opens the proposal first (is this the right problem?), then the delta (is done defined correctly?), then the code ([reviewing-changes.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/reviewing-changes.md), [team-workflow.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/team-workflow.md)). | Matches the roles in ADR-0004: Issue, wiki change, then code. The viewer could present a proposal in that order. |
| Right-size the change | A good change has one intent you can say in a sentence; signs it is too big are a scope that reads like a list, a review nobody will do, and two people who could not work on it without colliding ([writing-specs.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/writing-specs.md#right-size-the-change)). | Same rule as our split-by-independent-outcome guidance in ADR-0004, stated more memorably. |
| Conflicts in specs are a feature | Two changes that edit the same requirement conflict at merge, and the guide calls that git telling you two changes disagreed about how the system should behave ([team-workflow.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/team-workflow.md#two-people-parallel-changes)). | Supports ADR-0005's position that ordinary file overlap is handled at integration while behavioral disagreement needs resolution first. Wiki-page conflicts are that signal. |
| Explore before you propose | A read-only conversation that investigates the codebase, weighs options, and scopes the work, creating no artifacts until the picture is clear ([explore.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/explore.md)). | Our grilling skills already play this role; the explicit "explore costs nothing and commits you to nothing" framing is a good way to describe pre-pickup clarification. |
| Reconcile in whichever direction is true | When hand edits desync code and spec, either the spec is stale (update it) or the code drifted (fix it), and the spec must be honest before it becomes the truth of record ([editing-changes.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/editing-changes.md)). | Exactly the stance ADR-0004 takes on a bug against a correct contract. |
| Clarify with few, high-impact questions | Spec Kit's clarify pass scans a fixed taxonomy (scope, data model, UX flow, non-functional, integrations, edge cases, constraints, terminology, completion signals) and asks at most five questions, each answerable by a short choice, ranked by impact times uncertainty, then writes answers back into the spec ([clarify.md](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md)). | The taxonomy is a useful checklist for a Change or Investigation Issue before pickup. Our grilling skill asks the whole frontier; the cap and the write-back are the parts to borrow. |
| Unit tests for English | Spec Kit's checklist command validates the requirements text itself: are hover states defined for every element, is "prominent" quantified. It explicitly is not verification of the implementation, and only the reviewer may tick an item ([checklist.md](https://github.com/github/spec-kit/blob/main/templates/commands/checklist.md)). | A reviewer-owned quality checklist for a wiki page is cheap and fits the "review the contract, not the code" emphasis in ADR-0005. |
| Read-only analysis and append-only convergence | `analyze` reports inconsistencies across artifacts and never edits; `converge` compares the code with the spec and only appends remaining work as tasks, leaving `tasks.md` byte-identical when nothing is missing ([analyze.md](https://github.com/github/spec-kit/blob/main/templates/commands/analyze.md), [converge.md](https://github.com/github/spec-kit/blob/main/templates/commands/converge.md)). | Two well-bounded agent roles for a PR check: report drift between wiki and code, and list what the PR still owes its Issue. The write discipline (read-only, or append-only) keeps them safe to automate. |
| Verify along three axes | OpenSpec's verify reports completeness (tasks and requirements present), correctness (implementation matches intent, scenarios covered), and coherence (design decisions followed), with issues graded CRITICAL, WARNING, SUGGESTION and a bias toward the lower grade when uncertain ([verify-change.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/templates/workflows/verify-change.ts)). | A ready-made shape for the acceptance evidence a PR description should carry. |
| A versioned constitution | Project principles live in one file with a version, ratification date, and amendment date; every plan runs a constitution check gate and must justify violations in a complexity table ([constitution-template.md](https://github.com/github/spec-kit/blob/main/templates/constitution-template.md), [plan-template.md](https://github.com/github/spec-kit/blob/main/templates/plan-template.md)). Adoption guidance says to derive principles from what the repository already enforces and never invent standards to fill the template ([existing-projects.md](https://github.com/github/spec-kit/blob/main/docs/guides/existing-projects.md)). | Our ADRs and CONTEXT.md already hold this. The two transferable bits are deriving rules from existing evidence during setup, and a justification table when a change knowingly breaks a rule. |
| Roadmap as a shallow file with stable ids | For work too big for one session, a roadmap names and orders slices with an id, intent, scope boundary, dependencies, and status, but does not design them ([spec-of-specs.md](https://github.com/github/spec-kit/blob/main/docs/concepts/spec-of-specs.md)). | This is our wayfinder map; the guidance to reach for it only after lighter options fail is worth keeping. |
| Engine and steering wheel | OpenSpec splits a CLI that knows the rules (artifact shapes, dependencies, merge) from per-tool slash commands generated by `init`, so one workflow runs across thirty agents. Artifacts and their dependency order are declared in a `schema.yaml` anyone can edit ([how-commands-work.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/how-commands-work.md), [schema-yaml.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/schemas/schema-yaml.md)). | Confirms the direction of keeping deterministic wiki mechanics (indexes, link checks, drift) in a small tool while skills stay thin prompts. |
| Machine-readable surfaces | Every OpenSpec CLI command has a documented `--json` shape with a shared diagnostic envelope of severity, code, message, target, and fix ([agent-contract.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/agent-contract.md)). | If we build a wiki linter or drift checker, this envelope is a good contract for what it returns to agents and CI. |
| Three-step bug flow with honest verdicts | Spec Kit's bug extension separates assess (read-only), fix (the only step that edits code, bounded to the files the assessment named), and test, whose verdict is downgraded to partial if the reproduction was never exercised ([agentic-bugfix.md](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-bugfix.md)). | Maps onto our Bug template: the assessment is the evidence the Issue asks for, and "never over-claim the verdict" belongs in the PR's acceptance evidence. |

## What does not transfer

Spec Kit's per-feature artifact set duplicates context across features and needs its persistence-model choice precisely because there is no shared contract; the living-spec model it describes is what our wiki already is. Its templates carry numbered ids, priorities, and measurable success criteria that would make wiki pages heavier than [ADR-0006](../adr/0006-write-concise-linked-wiki-pages.md) wants. OpenSpec's archive step and `changes/` folder exist because the spec tree and the change are separate artifacts; with contract edits in the PR, git history is the archive. OpenSpec's architecture rationale page is an unwritten skeleton ([design-decisions.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/architecture/design-decisions.md)), so its design reasons are inferred from the docs rather than stated.

## Limits

These findings describe the tools as read from their repositories on 2026-09-12 and do not measure outcomes for teams using them. Neither tool addresses a graph viewer or a review lens over connected pages. No decision here has been made; the ADRs and the [open questions](../../.agents/handoffs/wiki-driven-dev-harness.md) remain the authority.
